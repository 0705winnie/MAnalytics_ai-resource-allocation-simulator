# Production Persistence Debugging Report

Date: 2026-08-10

Scope: simulation progress, monthly results, past submissions, instructor submissions, Instructor Student Progress, and leaderboard persistence.

This report is based on inspection of the current repository. No application code or database records were changed during the investigation.

## Executive summary

The application currently has three unrelated representations of a student result:

1. React memory stores the active simulation and completed months.
2. Browser `localStorage` stores History, saved monthly results, Past Submissions, and the student's leaderboard row.
3. PostgreSQL stores instructor-facing full-year summary submissions.

There is no persisted simulation session, PostgreSQL monthly-result table, final-submission concept, or shared student leaderboard. No stable run/session identifier connects these three representations.

## A. Current persistence architecture

| Data | Frontend state / localStorage | PostgreSQL | Backend endpoint | Restoration behavior |
|---|---|---|---|---|
| Current simulation month | Derived as `completedMonths.length + 1` | None | None | Resets to Month 1 whenever `App` remounts |
| Simulation session | `completedMonths` React state only | None | None | Never restored |
| Completed months | `completedMonths` React state | None | `POST /api/simulate/month` returns one stateless result | Never restored |
| Current policy | `policyCode` React state | None | Sent to simulation/submission endpoints | Resets to `POLICY_TEMPLATE` |
| Current parameters | `policyParams` React state | None | Sent with policy | Resets to `{}` |
| Monthly results in Simulation | Derived from `completedMonths` | None | Stateless simulation response | Lost on refresh |
| Monthly Results in History | Latest saved `submissionHistory` snapshot | None | None | Restored from the same browser's `localStorage` |
| Cumulative revenue in Simulation | Client aggregation of `completedMonths` | Only a separately recomputed submission total | None beyond monthly calls | Lost on refresh |
| Past Submissions in History | `submissionHistory` in `localStorage` | None | None | Restored only in that browser |
| Student leaderboard result | Best local saved history entry | None | No leaderboard API | Restored only in that browser |
| Classmate leaderboard rows | Hardcoded mock constants | None | No leaderboard API | Always the same sample rows |
| Instructor submission | Sends current policy and parameters | One summary row per click in `submissions` | `POST /api/submissions` | Visible only through Instructor Progress |
| Final submission | No frontend state | No table or flag | No endpoint | Does not exist |
| Instructor Progress | None | Derived from all `submissions` rows for course enrollments | `GET /api/instructor/courses/{course_id}/progress` | Refetched when instructor opens page |
| Authentication | React session plus HTTP-only JWT cookie | Users, courses, enrollments | `/api/auth/me`, login/logout | Authentication restores; simulation state does not |

Important implementation points:

- `src/App.tsx:18-28` initializes policy, parameters, and completed months without any persistence or recovery request.
- `src/lib/storage.ts:55-71` is the only History restoration logic.
- `src/pages/SimulationPage.tsx:328` derives the next month from the React array length.
- `src/types/simulation.ts:77-81` explicitly documents the client as the source of truth for prior months.
- `src/auth/AuthProvider.tsx:61-83` restores authentication through `/api/auth/me`, but does not request simulation state.

Backend memory is used only transiently while compiling and running an HTTP request. There is no in-process session cache.

### Actual relevant PostgreSQL schema

Only four relevant tables exist:

#### `users`

- UUID primary key.
- Globally unique normalized Berkeley username.
- Role, active status, password hash, and timestamps.

#### `course_instances`

- UUID primary key.
- Globally unique normalized course code.
- `created_by -> users.id`, `ON DELETE RESTRICT`.

#### `enrollments`

- UUID primary key.
- `course_id -> course_instances.id`, `ON DELETE RESTRICT`.
- `user_id -> users.id`, `ON DELETE RESTRICT`.
- Unique `(course_id, user_id)`.
- Unique `(course_id, nickname_normalized)`.
- Activation, status, nickname, and timestamp fields.

#### `submissions`

- UUID primary key generated by the application.
- `enrollment_id -> enrollments.id`, `ON DELETE RESTRICT`.
- `total_revenue`.
- `total_unfinished_requests`.
- `total_unfinished_value`.
- `warnings_count`.
- `submitted_at`, server default `now()`.
- Non-unique index on `enrollment_id`.
- No uniqueness constraint preventing repeated submissions.

The schema is defined in:

- `backend/alembic/versions/0001_create_users_courses_enrollments.py`
- `backend/alembic/versions/0002_submissions.py`

There are no tables for simulation sessions, monthly results, policy versions, completed stages, leaderboard records, or final submissions.

## B. Problem 1 root-cause analysis

Refresh resets the simulator to January because active progress exists only in React memory.

`App` mounts with:

- Template policy.
- Empty parameters.
- Empty messages.
- Empty `completedMonths`.

The next month is calculated as `0 + 1`. There is no `useEffect` or backend recovery endpoint for a simulation session.

The data that appears to survive is different data:

- History Monthly Results and Past Submissions come from the `submissionHistory` localStorage key.
- The student's leaderboard row is calculated from the best entry in that same local history.
- Mock classmate rows are hardcoded.
- Instructor submission rows remain in PostgreSQL but are not loaded into the student UI.

After rerunning:

- Nothing updates History until the student clicks **Save to My History**.
- Clicking **Submit Result** does not update local History.
- Clicking **Save to My History** does not submit to PostgreSQL.
- The leaderboard shows the best local saved run, not necessarily the newest run. A lower-scoring rerun will not change the leaderboard score.
- History Monthly Results shows the newest local save, not the newest instructor submission.

The two independent button paths are implemented in `src/pages/SimulationPage.tsx:365-390`.

## C. Problem 2 root-cause analysis

The student and instructor are not displaying the same calculation.

### Student calculation

The visible cumulative result is the sum of however many monthly calls are currently present in `completedMonths`. This calculation is implemented by `aggregateMonths()` in `src/pages/SimulationPage.tsx:82-106`.

The visible result may represent:

- A partial 1-11 month total.
- A 12-month run in which the student revised the policy between months.
- A continuation that uses client-supplied prior-month history.

### Instructor submission calculation

The submission request sends only the current `policy_code` and `params` from `src/pages/SimulationPage.tsx:372-390`.

`backend/app/routers/submissions.py:38-54` then runs that one current policy from scratch for all 12 months and stores only its summary totals.

A mismatch is therefore expected whenever:

- The student submits after fewer than 12 months. Submission is enabled after only one month.
- The policy was changed between completed months.
- Parameters were changed between months.
- The visible or locally saved result belongs to an older run.
- The current policy differs from the policy snapshot saved to local History.

The frontend discards the returned submission totals and displays only `Submitted` confirmation, so the student is not shown the value that was actually stored.

### Repeated submissions

Every click creates a new database row. There is no upsert and no applicable unique constraint.

Instructor Progress:

1. Loads all enrollments for the course.
2. Loads every submission for those enrollment IDs.
3. Sorts by `submitted_at ASC`.
4. Uses the last row as latest.
5. Independently uses the maximum revenue as best.

Relevant code:

- `backend/app/routers/instructor_progress.py:58-67`
- `backend/app/schemas/instructor_progress.py:23-40`

It does not read a simulation session, monthly aggregation, final flag, or local History.

Duplicate rows are counted but not summed. However, latest ordering is not fully deterministic because it orders only by `submitted_at`; there is no ID tie-breaker for identical timestamps.

## D. Problem 3 root-cause analysis

The responsible endpoint is:

```text
POST /api/submissions
```

The frontend shows `The backend did not respond as expected (HTTP 500)` when a failed response lacks a JSON `detail` field. That means the observed response came from an unhandled backend exception rather than a normal authentication, validation, or compilation rejection.

### Conditions the current code largely rules out

- Duplicate submissions are allowed.
- There is no unique student/course/session/month submission key.
- The endpoint does not require a simulation-session row.
- Course ownership comes from the authenticated enrollment, not the request body.
- User, enrollment, and course claims are checked by authentication and normally produce a structured 401 on mismatch.
- Missing or inactive enrollment also normally produces a structured 401.
- Submission IDs use random UUIDs; collision is not a credible student-specific explanation.

### Unhandled paths

The endpoint catches only policy compilation errors. It does not catch or roll back:

- Full-year simulation failures outside the policy-call wrapper.
- `SQLAlchemyError` from `db.commit()`.
- Foreign-key violations caused by a race or stale state.
- Undefined-table or schema-drift errors.
- Database connection or timeout errors.
- Errors from `db.refresh()`.
- Response serialization failures.

The failing code is most likely within `backend/app/routers/submissions.py:43-55`, particularly `db.commit()`.

`render.yaml` also does not run `alembic upgrade head` during build or startup. An unapplied or inconsistent `0002_submissions` migration is therefore a significant deployment risk. If Student A definitely received a successful 201 response from this same service and database, a completely missing `submissions` table is ruled out and the full Render traceback is required to identify the exact exception.

### Render logs to capture

Find the request line:

```text
POST /api/submissions ... 500 Internal Server Error
```

Capture the complete exception that follows:

```text
ERROR: Exception in ASGI application
Traceback ...
```

Specifically look for:

- `psycopg.errors.UndefinedTable: relation "submissions" does not exist`
- `sqlalchemy.exc.ProgrammingError`
- `psycopg.errors.ForeignKeyViolation`
- `sqlalchemy.exc.IntegrityError`
- `sqlalchemy.exc.OperationalError`
- `SSL connection has been closed unexpectedly`
- `connection timed out`
- `ResponseValidationError`
- A traceback into `run_full_simulation`
- A traceback ending at `db.commit()` or `db.refresh()` in `submissions.py`

Record the timestamp and final exception/cause. Do not record the JWT, database URL, passwords, or submitted policy source.

## E. Problem 4 root-cause analysis

There is no shared leaderboard query to trace.

`src/pages/LeaderboardPage.tsx` defines four hardcoded mock classmates and creates one current-browser row from local saved History. There is no frontend leaderboard API call, backend leaderboard router, SQL query, or database leaderboard table.

Consequently:

- Student A and Student B being in the same course has no effect.
- Course, enrollment, student, session, and submission IDs are never used by the leaderboard.
- Final submission is not required because final submission does not exist.
- Twelve completed months are not required.
- Same-stage student filtering does not exist.
- `Same-Month Benchmark Comparison` compares a student against fixed baseline algorithms, not other students.
- Student B cannot see Student A because Student A's localStorage is unavailable in Student B's browser.

## F. Relationship between the problems

Problems 1, 2, and 4 are direct consequences of the split persistence architecture. Problem 3 occurs in the only new bridge to PostgreSQL, but that endpoint is disconnected from the student's actual simulation session and lacks a complete transaction/error boundary.

```text
React monthly run
    |-- Save to History --> browser localStorage
    `-- Submit Result ----> recompute a different 12-month run --> PostgreSQL

History/Leaderboard reads localStorage
Instructor Progress reads PostgreSQL
```

There is no stable run/session identifier connecting any branch.

## G. Recommended repair order

1. Reproduce Student B's 500 and capture the full Render traceback. Verify the deployed Alembic revision and actual `submissions` schema before changing behavior.
2. Add guarded deployment migration execution and transaction handling that rolls back and logs the real database failure without falsely returning success.
3. Introduce PostgreSQL simulation-session and monthly-result persistence, with an authenticated restoration endpoint.
4. Persist policy and parameter snapshots per month so an official result represents what was actually run.
5. Define submission semantics: completed-session submission, repeated-attempt rules, idempotency, and explicit final selection.
6. Make Instructor Progress read the same persisted run/submission object with deterministic `(submitted_at, id)` ordering.
7. Implement course-scoped same-stage and final leaderboard backend queries.
8. Switch student History and leaderboard UI to backend data. Retain localStorage only for explicitly non-authoritative drafts.
9. Remove mock leaderboard and sample-submission behavior after backend recovery is proven.
